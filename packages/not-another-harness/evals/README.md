# Harness real-task evaluations

Run the deterministic harness regression tasks with `pnpm --filter @astracollab/not-another-harness exec vitest run test/evals.test.ts`.

The deterministic suite covers a targeted bug fix, a new regression test, and a behavior-preserving refactor. Each task starts from a temporary workspace and checks the resulting files, completed stop reason, model-step count, and cumulative token accounting. It exercises the harness and built-in tools with scripted model responses.

## Live model evaluations

Set `NAH_EVAL_MODEL` to a fixed `provider:model-id` supported by the CLI, configure its API key, and run:

```sh
NAH_EVAL_MODEL=anthropic:claude-sonnet-4-5 \
NAH_EVAL_REPEATS=3 \
pnpm --filter @astracollab/nah exec vitest run test/live-evals.test.ts
```

The opt-in suite runs each selected task from a fresh temporary workspace and independently executes its acceptance script. It currently covers numeric clamping and invalid inputs, strict port parsing, and optional-name normalization. Runs repeat three times by default; set `NAH_EVAL_REPEATS` to an integer from 1 to 20. Use `NAH_EVAL_TASKS=clamp-boundaries,strict-port-parser` to select task IDs.

Every repetition appends one JSON object to `packages/not-another-harness/evals/live-results.jsonl` (override with `NAH_EVAL_RESULTS`). Records include a run ID, exact model spec, task ID, repetition, pass/fail, stop reason, steps, tool-call count, input/output/total tokens, whether usage is estimated, elapsed milliseconds, and acceptance-check output. Each record also identifies the source revision and whether the working tree was dirty. The suite appends one per-task summary row with pass rate and median steps, tool calls, tokens, and latency for that run's repetitions. For comparable results, keep the model spec, task definitions, and repeat count fixed and run from a clean revision. The default metrics file is generated by a live run and ignored by source control; choose a separate result path for a baseline you intend to retain.

Example custom output location:

```sh
NAH_EVAL_MODEL=openai:gpt-4.1 \
NAH_EVAL_REPEATS=5 \
NAH_EVAL_RESULTS=/tmp/nah-eval-baseline.jsonl \
pnpm --filter @astracollab/nah exec vitest run test/live-evals.test.ts
```

## Live memory evaluation

`packages/nah/eval-memory.mts` proves whether memory actually carries information
forward, or whether the conversation transcript is doing all the work.

It teaches facts containing **unguessable tokens** (so the agent cannot confabulate
a plausible-looking answer), then **wipes the conversation history** and asks again.
With an empty transcript, anything recalled came out of memory.

```sh
cd packages/nah
npx tsx eval-memory.mts                        # teach, wipe, recall
NAH_EVAL_RECALL_ONLY=1 npx tsx eval-memory.mts # fresh process, memory from disk
NAH_MEMORY_DEBUG=1 npx tsx eval-memory.mts     # per-turn extraction/promotion trace
```

Use real, non-guessable values. A recall test built from a plausible URL or path
passes whether or not memory works, because the model will invent one — an early
version of this eval reported 3/3 using values the agent had simply guessed.

`eval-memory.mts` also proves the `recall` tool path: one recall question is
deliberately worded unlike the stored memory ("Which opaque identifier was issued…"
versus "The staging build ID is …") so pre-staging cannot rescue it, and the run
reports how many times the agent invoked the tool.
